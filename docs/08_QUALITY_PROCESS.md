# 08. 质量、配置管理与文档流程

> D1 · 2026-09-23 · 本项目采用的轻量工程流程，不代表任何质量体系认证。

## 1. 文档基线与权威来源

| 内容 | 权威文件 | 关联更新 |
|---|---|---|
| 必需/可选范围与阶段 | PRD | SRS、计划、手册 |
| 需求 ID 与通过条件 | SRS | 追踪矩阵、测试计划 |
| 线程/模块/状态规则 | HLD + LLD | 测试、实现 |
| 字节与消息语义 | 协议规格 | 模拟器、Codec、固定向量 |
| schema/迁移/查询 | 数据库设计 | Repository、测试 |
| 运行路径与默认参数 | 配置契约 | 手册、校验器、测试 |
| 结果 | 有实际运行记录的报告 | 追踪状态、README、发布说明 |

D1 是文档版本，协议 Version=1、JSON schema_version=1、数据库 user_version=1 是三个独立版本，不得互相替代。日期记录文档基线开始日；本轮完成与校验时间见 [评审记录](14_DOCUMENT_REVIEW.md)。

## 2. 最小流程与版本控制

需求 → 设计/评审 → 编码 → 单测 → 集成 → 修复/回归 → 发布。沿用 main、develop、feature/*、fix/* 约定；使用 feat/fix/test/docs/refactor/build 前缀。提交、推送、打标签由用户明确授权后执行，文档列出流程不意味着已执行。

每阶段代码应可编译；纯文档阶段没有 CMake 时如实记“不可执行产品构建”，不能生成通过标记。

## 3. 追踪矩阵维护

[TRACEABILITY_MATRIX.csv](../templates/TRACEABILITY_MATRIX.csv) 每个 SRS 需求一行，保留原列：Requirement ID、Requirement、Design Module、Implementation、Test Case、Status。

- Test Case 使用完整 ID，用分号分隔，不写 TC-PROTO-001/004 等需猜测的缩写。
- Implementation 在源码存在后填实际路径/符号或提交；当前留空，不能把规划路径当实现。
- Planned → Implemented → Verified。Verified 需全部适用用例通过，并在实现/证据字段关联运行报告；失败修复前回到 Implemented。
- 每次新增需求同步测试和矩阵；删除/降级必需项需用户确认，保留变更理由。
- 测试执行状态与需求状态不同：Not Run/Pass/Fail/Blocked/N/A 见测试计划。

## 4. 变更与审查

不兼容协议、schema 迁移、线程模型、必需范围或验收门槛变化写决策记录：背景、方案、选择、影响、回退与验证。不为普通措辞修订引入复杂审批。

审查重点：

- RAII 与 QObject parent-child 所有权是否一致，避免双重释放；不机械地把所有 QObject 套 shared_ptr。
- worker/socket/timer/SQL 连接是否在所属线程使用与销毁；退出顺序是否有死锁。
- 每一级外部长度是否先校验，内存/队列/日志是否有上限。
- 命令超时是否与设备未执行区分，重试是否重复产生副作用。
- 数据库异常是否回滚，是否吞掉错误或静默丢数据。
- 错误/状态是否有日志与用户可见结果，对应测试是否能复现。
- 新默认值是否同步配置、协议、测试，是否把计划误写成成果。

## 5. 发布检查

只有获得实际证据才勾选：

- [ ] Windows/Ubuntu，Debug/Release 编译与 CTest。
- [ ] 协议、状态机、告警、配置、数据库核心测试。
- [ ] TCP/UDP/串口集成；虚拟与实物范围明确。
- [ ] 10 设备 30min 性能和 8h 稳定性；无未关闭 P0/P1。
- [ ] schema/version/配置模板一致，旧数据兼容和迁移证据。
- [ ] 干净环境插件、动态库、可写目录、首次启动和退出验证。
- [ ] 用户手册填入实际程序名/命令、版本和故障定位方法。
- [ ] 发布清单记录文件 SHA256、工具链、源码基线、测试报告和已知限制。
- [ ] 用户授权后才创建提交/标签/发布；不得把示例 v0.1.0-rc1 写成现存版本。

## 6. 对质量过程的表述

只有实际执行后才在 README 或发布说明中描述“完成需求追踪、评审、测试和缺陷闭环”。本项目未经任何质量体系认证，不由文档数量推断过程能力。
